Um teto em DIAS não protege: 31 dias já estouram em julho. O teto tem de ser

# P1-42 · Rate limit do login é contornável com um header — furo no P1-5

**Categoria:** Segurança · **Severidade:** P1 · **Esforço:** 30min

## O defeito

`routes/index.js:44-47`:

```js
function _loginKey(req, username) {
  const ip = req.headers['x-forwarded-for'] || req.socket?.remoteAddress || 'unknown';
  return `${ip}|${username || '?'}`;
}
```

`x-forwarded-for` é um header **enviado pelo cliente**. Ele tem precedência sobre
o IP real da conexão e não é validado em lugar nenhum. Não existe
`app.set('trust proxy', ...)` no `server.js`.

## Como se contorna

A chave do balde é `IP|username`. Trocando o header a cada request, cada
tentativa cai num balde novo, que sempre começa em `count: 1` — **o teto de 10
tentativas por 5 min nunca é alcançado**:

```bash
for i in $(seq 1 100); do curl -s -X POST http://localhost:3002/api/auth/login -H "Content-Type: application/json" -H "X-Forwarded-For: 10.0.$((i/256)).$((i%256))" -d '{"username":"admin","password":"tentativa'$i'"}' -o /dev/null -w "%{http_code} "; done; echo
```

Esperado hoje: **cem `401`, nenhum `429`**. O P1-5 está marcado done e o throttle,
na prática, não existe.

Agrava: `_verifyPassword` (`middleware/auth.js:135`) ainda aceita SHA-256 legado
sem salt — e o `.env` de produção **não migrou pra scrypt** (pendência aberta do
próprio P1-5). SHA-256 sem salt é barato de testar em volume.

# P2-41 · Nenhum handler de `unhandledRejection` — a próxima promise solta derruba o processo

**Categoria:** Ops · **Severidade:** P2 · **Esforço:** 30min · **Preventivo**

## O achado

```bash
grep -rn "unhandledRejection\|uncaughtException" --include=*.js . --exclude-dir=node_modules
```

Não retorna nada. A VM roda **Node 24**, onde o default de `unhandledRejection` é
`throw` — ou seja, **uma promise rejeitada sem `.catch()` mata o processo**.

**Sendo justo com o código atual: não achei uma promise solta hoje.** Os
`fire-and-forget` do `runSnapshot` (`services/cronService.js:255-296`) todos têm
`.catch()`, e os helpers `_record*` (`cronService.js:33-110`) têm `try/catch`
interno que engole até o Postgres fora do ar. Isso é cuidado real, e é por isso
que este item é P2 e não P1.

O problema é que **o cuidado é manual e não tem rede de proteção**. O próximo
`.then()` sem `.catch()`, escrito por qualquer pessoa ou por qualquer IA, deixa
de ser um erro logado e passa a ser uma queda.

## Por que a queda não é barata

1. `_acc` vive em memória (P1-13): restart **subnotifica produção do dia**.
2. `services/cronService.js:1506` — `setTimeout(runSnapshot, 5000)` no boot. Se a
   causa da queda for determinística (Postgres fora, por exemplo), é crash →
   restart → crash em 5s → **crash loop**.
3. O PM2 desiste depois de N restarts rápidos: aí não é um ciclo perdido, é o
   **painel fora do ar**.

É exatamente o encadeamento do incidente de 09/07/2026 (P0-0), e o `autorestart`
do PM2 não protege contra ele — participa dele.

## Correção

No `server.js`, **antes** de `async function start()` (linha 168):

```js
// ── REDE DE PROTEÇÃO DE PROCESSO (28/08/2026, P2-41) ─────────────────────────
// Node 24 derruba o processo numa promise rejeitada sem catch. Hoje nenhuma está
// solta — mas a próxima que alguém escrever vira queda, e queda tem custo: `_acc`
// é em memória (P1-13), então restart SUBNOTIFICA a produção do dia; e o
// setTimeout(runSnapshot, 5000) do boot faz erro determinístico virar crash loop
// até o PM2 desistir. Logar e seguir é estritamente melhor que morrer.
//
// `uncaughtException` é outra história: depois dele o estado do processo é
// indefinido. Aí saímos DE PROPÓSITO e deixamos o PM2 subir limpo — mas com a
// causa no log, que é o que faltava.
process.on('unhandledRejection', (reason, promise) => {
  const msg = reason instanceof Error ? (reason.stack || reason.message) : String(reason);
  console.error('[FATAL] unhandledRejection — promise sem catch:', msg);
  console.error('[FATAL] promise:', promise);
  // NÃO derruba: um ciclo de cron perdido é melhor que o painel fora do ar.
});

process.on('uncaughtException', err => {
  console.error('[FATAL] uncaughtException:', err.stack || err.message);
  console.error('[FATAL] estado do processo é indefinido — saindo pro PM2 reiniciar.');
  process.exit(1);
```

# P3-17 · `memoCache` envenena a chave pra sempre se a função lançar de forma síncrona

**Categoria:** Backend · **Severidade:** P3 · **Esforço:** 15min · **Latente**

`services/memoCache.js:63-73`:

```js
      const promise = (async () => {
        try {
          const value = await fn(...args);
          store.set(key, { value, expiresAt: _now() + ttlMs });
          _prune();
          return value;
        } finally {
          inflight.delete(key);
        }
      })();
      inflight.set(key, promise);
```

Corpo de função `async` roda **síncrono até o primeiro `await`**. Se
`fn(...args)` lançar **de forma síncrona**, o `finally` executa **antes** do
`inflight.set(key, promise)` — o `delete` não acha nada, e logo em seguida o
`set` grava uma **promise já rejeitada que nunca mais é removida**. Toda chamada
seguinte com aquela chave cai no `if (inflight.has(key))` e recebe a rejeição.
Envenenada até o restart do processo.

**Não é explorável hoje:** os três consumidores
(`db/deslocamentosQueries.js:512-518` — `listDeslocamentos`, `rankingEquipes`,
`tendenciaDiaria`) são `async`, e função `async` nunca lança síncrono: devolve
promise rejeitada. O bug fica esperando o primeiro consumidor não-`async`.

Correção — registre o in-flight **antes** de começar:

```js
      // 28/08/2026 — P3-17. `inflight.set` vinha DEPOIS da IIFE. Se `fn` lançasse
      // de forma síncrona, o `finally` rodava antes do `set` e a chave ficava com
      // uma promise rejeitada pra sempre. Hoje os 3 consumidores são async (que
      // nunca lança síncrono), então é latente — mas o custo de fechar é zero.
      let resolveP, rejectP;
      const promise = new Promise((res, rej) => { resolveP = res; rejectP = rej; });
      inflight.set(key, promise);
      (async () => {
        try {
          const value = await fn(...args);
          store.set(key, { value, expiresAt: _now() + ttlMs });
          _prune();
          resolveP(value);
        } catch (err) {
          rejectP(err);
        } finally {
          inflight.delete(key);
        }
      })();
      return promise;
```

**Aceite:** teste com `fn` que lança síncrono; a 2ª chamada com a mesma chave
**re-executa** `fn` em vez de devolver a rejeição velha. **Rollback:** `git revert`.
